## 二、三档该暴露什么（重新归类）

现在的毛病：分组按**后端字段**（prompt / lyrics / tags / mood / bpm / sec / count / persona / seed），
不按用户心智。于是出现三件荒唐事：① **性别（女声/男声）被塞进「风格点缀」**；② 「人声」组里只有
`人声演唱/纯音乐`，所以**"纯音乐 + 女声"这种矛盾组合能同时选中**；③ 想要"微醺"的人无处可选，
被迫选"忧郁"，拿到一首苦情歌（用户当场反馈"这旋律风格不喜欢"，是对的）。

### 统一六组（模型一份，三档只差默认值与折叠）

| 组 | 内容 | 简约 | 标准 | 深度 |
|---|---|---|---|---|
| **01 感觉** | 一句话 + 心情（25 档，含新增「微醺」） | 一句话 + 4 个心情胶囊 | 心情全量多选 | +词典外自由心情（逃生口），并**明示**"我替你加了这些配方词" |
| **02 唱什么** | 主题 / 歌词 | 主题词（AI 写词） | +自己填词、段落模板 | +`[Verse]/[Chorus]` 标记、语言、韵脚提示 |
| **03 谁在唱** | **人声组（新）**：`有人声 / 纯音乐` + **女声 / 男声 / 童声 / 合唱** + 声音人格 | 有人声/纯音乐（二选一） | +性别四选 | +人格库（参考音 `ref_audio`）、音色强度 |
| **04 什么风格** | 曲风 ≤3 + 质感（乐器/混音）≤3 | 4 个常见曲风胶囊 | 曲风 18 全量 | +质感 24 全量、自由补充 |
| **05 快慢长短** | BPM、时长 | 「慢/中/快」+ 30/60/90/120s | BPM 数字 + ≤180s | BPM 60–180、时长 ≤240s、seed |
| **06 出几首 · 花费** | 候选数、**价格与余额** | 三档共用一条：`15⚡/首 × N = 合计 · 余额 X · 不足给出路`（现在**任何一档都不显示**） |

三条硬规矩（写进契约与测试，不靠自觉）：

1. **上限必须等于能真交付的上限**。引擎/显存给不了 240 秒，滑块就不许出现 240 —— 宁可只到 180，
   也不许"拉得满、拿一半"。同理：App 可选 tags 之和 = 服务端 cap（已由 V31-③ 用读源码的方式钉住）。
2. **机器猜测永远只能是补充，不许挤掉用户手选**；并且要把"补了什么"显示出来（猜测词打标 `AI 加`）。
3. **性别走人声通道，不走风格 tags**：`人声/纯音乐 + 性别` 是同一组的两级，选"纯音乐"时性别置灰；
   派单侧优先用 `ref_audio`（人格）与 caption 双写，tags 只作辅助 —— 因为今天证明了：
   **`female vocal` 排到 tags 第一位，两首里仍出一首偏男声（F0 中位数 157Hz vs 女声 222Hz）**。

### 顺带要测/要修的三档一致性问题（今天没来得及）

- 切档时已填字段是否保留（简约填了灵感 → 切深度，内容还在不在）；
- 三档价格与每日 50⚡ 免费额度的关系（深度 4 首 = 60⚡ > 50⚡，**结构上必然失败**，见 §三-3）；
- 简约档 `shell_easy.dart:97-99` 空 prompt 直接 `return`（静默无反馈），与深度档一样缺"为什么不能点"。
